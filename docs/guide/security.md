# Security

Cluub blocks several classes of mistakes before your code runs, through compile-time rules, generated validation and safe UI rendering, and its server ships with sensible HTTP defaults. Other protections a production web app needs are **not built yet**. This page lists both, checked against the 0.1 source code and by sending real requests to a running server, with mitigations for each gap. If you only read one section, read [What is not there yet](#what-is-not-there-yet).

## What is protected today

### Text is rendered as text, never as HTML

Every value a view shows, such as `text todo.title`, `heading "Hi {name}"` or a button label, becomes a DOM **text node** (`document.createTextNode`). The UI runtime never uses `innerHTML`, and the language has no element that renders raw HTML. A todo titled `<img src=x onerror=alert(1)>` shows up as those characters on screen.

Attributes such as `placeholder`, `alt`, `class` and `aria-label` are set with `setAttribute`, and event handlers are only ever functions generated by the compiler, never strings from data.

### `javascript:` URLs are neutralized

For the `href` of `link ... to` and the `src` of `image`, the runtime replaces any value that starts with `javascript:` (ignoring case and leading spaces) with `#`. So `link "Website" to user.website` can't run script even when `website` came from a user. The page's Content-Security-Policy (below) blocks inline script as a second line of defense.

### Secrets stay on the server

| Rule | What it stops |
|---|---|
| **E204** | `ask ai` in a page, component or layout. AI calls are only allowed in services, apis and clients, so provider keys never ship to the browser |
| **E205** | reading `env.NAME` in the UI layer |
| **E401** | text that looks like a key, written in code: `sk-ant-…`, `sk-…` (20+ chars), `AIza…`, `ghp_…`, `xoxb-`/`xoxp-…` |
| Layer rules **E201** | a page using a store, client or service directly. Pages reach data only through an `api` |

The browser bundle (`dist/public/`) contains only models, pages, components, layouts and the *shape* of your api routes. Service code, store file paths, client base URLs and headers exist only in `dist/server.js`, outside the public folder.

E401 only recognizes those five patterns, and only in text literals. A password or an AWS key typed into a string isn't detected. Nothing stops an api from *returning* a secret either (`return env.SECRET`), so review what your apis send back.

### AI keys are never stored by Cluub

Cluub never ships, proxies or stores AI keys. Developer keys live in `.env` (written with mode 600 and git-ignored by `cluub ai set`) or in real environment variables. With `aiKeys "user"` or `"either"`, an end user's key stays in their browser and reaches your server only in the `X-Cluub-AI-Provider` / `X-Cluub-AI-Key` headers of their own requests. The server scopes it to that request with `AsyncLocalStorage`, never writes it to disk or to the log, and never echoes it back. Serve such apps over HTTPS and don't log request headers in proxies. Full details: [Your own AI keys](/guide/ai-keys).

### Input is validated at the api boundary

Before your route code runs, the dispatcher checks every declared parameter (path, query string or JSON body) against its type: `text`, `number`, `bool`, `email`, `url`, `date`, `list of T`, or a model. A missing value gives `400` with `Missing required value "title"`. A wrong type gives `400` with the field name, for example `total must be a number (got "abc")`. Body fields you didn't declare are ignored, not passed through.

Creating a model validates every rule (`required`, `min`, `max`, `one of`, `email`, `url`, `date`) and **rejects unknown fields** (`Todo has no field "isAdmin"`). Stores re-validate on `add` and `update`, so a request can't sneak extra properties into stored data.

### HTTP defaults

We verified each of these with `curl` against `cluub start`:

| Behavior | Response |
|---|---|
| Body larger than 1,000,000 bytes | `413 too_large`, and the connection is closed |
| Body without `Content-Type: application/json` (for example `text/plain`) | `415 bad_content_type` |
| Body that isn't valid JSON | `400 bad_json` |
| Malformed percent-encoding in the URL (`/%E0%A4%A`) | `400 bad_url` |
| Wrong method on a known path | `405`, naming the allowed methods (`Use GET or POST.`) |
| Every response | `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY` |
| HTML pages | `Content-Security-Policy: default-src 'self'; img-src 'self' data: https:; style-src 'self'; script-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'` |
| Static file paths | normalized, and they must stay inside `dist/public` (otherwise `403`) |
| `.clb` sources, `.env`, `dist/server.js`, `storage/` | never served |

Bodies are read as bytes and decoded once, so non-ASCII text (`café crème`) arrives intact. The JSON-only rule matters for CSRF: a browser can't send `Content-Type: application/json` to another site without a CORS preflight, which the server never approves. So a hostile page can't trigger your POST, PUT, PATCH or DELETE routes with a form or a simple `fetch`. The CSP has no `'unsafe-inline'`. The app boots from `/_cluub/boot.js`, and we confirmed in a browser that pages render under this policy with no console errors.

### Error messages don't leak internals in production

| Error | Status | Message sent to the client |
|---|---|---|
| Validation, `require` | 400 | your message or the rule's message |
| `fail "..."` | 400 or the status you gave, **any** status | your message, always |
| `Store.get` on a missing id | 404 | `Todo "17" was not found` |
| AI failure | 502 | `cluub start`: `The AI service is not available right now. Please try again.` · `cluub dev`: the real reason |
| `client` (outside API) failure | 502 | `cluub start`: `An outside service is not available right now. Please try again.` · `cluub dev`: the real reason |
| Any other exception (a bug) | 500 | `cluub start`: `Something went wrong on the server.` · `cluub dev`: `Unexpected error in TodoApi.add: <message>` |

The full error is always printed in the server log, for example `✗ TodoApi.summary: No API key for claude. Add ANTHROPIC_API_KEY=... to your .env file`. Under `cluub dev`, the first stack lines are printed too. Messages you write with `fail` are meant for users, so they're always shown. Don't put internal details in them.

### File stores write atomically and load safely

A store saved to JSON writes a temporary file and renames it over the real one, so a crash or power loss mid-write never leaves a half-written file. Stores load when the server starts, every record is validated against the model, and a broken file stops startup with a clear message instead of serving bad data.

## What is not there yet

Here is what Cluub 0.1 does **not** do, and what to do instead.

### No authentication, sessions or roles

Every api route is public. There is no login, session cookie, token check or `for role "admin"` (auth is on the [roadmap](/reference/roadmap)).

**Mitigation:** only deploy apps that are fine being public, or put authentication in front of the whole app: HTTP basic auth or an SSO proxy (oauth2-proxy, Cloudflare Access, a VPN) in your reverse proxy. Apis can't read cookies or headers today, so don't try to build password checks in Cluub code.

### No rate limiting

Nothing limits how often a client calls an api. This matters most for routes that call an AI provider, because every request costs money.

**Mitigation:** rate-limit in the proxy (the [nginx example](/guide/deployment#behind-a-reverse-proxy-nginx) does), set spending limits with your AI provider, and put `require text.count <= N` on prompt inputs (the `ai-chat` template does).

### No CORS configuration

The server sends no `Access-Control-Allow-*` headers. Browsers block other origins from calling or reading your api, which is the safe default and part of the CSRF protection above. You can't open the api to another frontend without a proxy that adds the headers, and adding them weakens that protection.

### No HTTPS termination

The server speaks plain HTTP.

**Mitigation:** terminate TLS in a reverse proxy or your platform, and add `Strict-Transport-Security` there once HTTPS works.

### Dev mode shows error details and listens on every interface

`cluub dev` sends real error messages (including AI and outside-API details) to the browser and, like `cluub start`, binds to all network interfaces. Anyone on the same network can reach a dev server.

**Mitigation:** never expose `cluub dev` publicly. Use `cluub build` + `cluub start` (or `node dist/start.mjs`) for anything shared.

### Types are only enforced at boundaries

Values are checked when a model is created, when an api receives parameters and when a store saves. Return types (`-> Todo`), page state and component properties aren't checked, so a service can return the wrong shape without an error. Write service and api tests for important responses ([Testing strategy](/guide/testing-strategy)).

### Other things to know

* **AI prompt injection.** User text you interpolate into a prompt can try to steer the model. Prefer `as Model` or `as one of [...]`: the reply is validated against your model or list, so a manipulated answer still has to fit the shape.
* **`cluub make` sends your code to the AI provider:** every `.clb` file in the project plus `LANGUAGE.md`. It doesn't send `.env`. Files are written only when the result compiles, only `.clb` files, and never paths containing `..` or absolute paths.
* **Crashes.** The server has no automatic restart. Run it under a supervisor (systemd `Restart=always`, Docker `--restart`).
* **No dependency risk:** Cluub and its output have zero npm dependencies, so there is no third-party supply chain to audit.

## Checklist before going live

1. `cluub build`, then `cluub start` or `node dist/start.mjs`. Never `cluub dev`.
2. TLS, gzip and rate limiting in a reverse proxy.
3. Authentication in front of the app if the data isn't public.
4. Secrets in environment variables (they override `.env`). Never commit `.env`; it's in `.gitignore` by default.
5. A supervisor that restarts the process.
6. Backups of `storage/`.
7. Review what each api returns and what each `fail` message says. Both reach the browser.
